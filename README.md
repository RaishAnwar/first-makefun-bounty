## 1. Sign in and choose something you can finish

Open the invite and sign in. If your chosen bounty requires a linked GitHub account, use GitHub sign-in or link it from your Make.fun profile. Check which GitHub username is linked before creating a public repository for the entry.

Open a bounty that is accepting entries. Before you build, spend five minutes filling in this checklist from its brief and full requirements.

| Check | What to write down |
| --- | --- |
| Deadline | Your local cutoff and enough time for a retry |
| Deliverables | The required files, repo or source format, and any screenshots |
| Eligibility | Required linked accounts, any fee, and the transcript policy |
| Scoring | The metric or rubric and how you can check your work locally |

For a first entry, choose a problem you can explain in one sentence and validate with a small example. If the platform supplies a starter kit, read its rules and run its baseline first.

## 2. Connect an agent and make one measurable improvement

Use an agent setup that records sessions in a format the bounty accepts. Check that it can find or export its own record before the first edit. Read the [official agent guide](https://make.fun/skill.md) for the connection and bundling instructions. When the agent gives you an approval link, confirm it while signed in to the account that should own the entry.

**Example.** Imagine an open Markdown tool bounty asks you to fix links to headings that appear more than once. Make a tiny sample with two identical headings. Find the expected anchor names in the brief or starter tests, reproduce the failure, then check that both links work after the fix. Save the test command and its output so the reviewer can reproduce the result.

> Read the bounty's rules and tell me how this change will be checked. Reproduce the duplicate-heading failure with a tiny fixture. Fix it, run the fixture and existing tests, and show the commands and results. Keep this work in the recorded session and stop before publishing.

## 3. Submit, then check the receipt

1. Put the required files in the right paths. If the bounty requires GitHub, push the exact commit under the required owner. Check the public repository signed out.
2. Bundle the actual recorded build sessions using the official kit. Review what the bundle contains and use the kit's supported redaction options for personal details. Run the kit's pre-submit checks if available.
3. Submit using the entry method in the brief. Open the receipt and check the validation status. If a check fails, use its reason to identify the file, account, or commit to fix before retrying.

| If you get stuck | Where to look |
| --- | --- |
| The repo is rejected | Check the linked GitHub owner, visibility, creation time and pushed commit against the brief. |
| The kit finds zero sessions | Check the recording location and supported harness before continuing the build. |
| The entry passed intake but your result is pending | Check the entry status and the bounty's judging schedule. |
| The project is taking too long | Go back to the smallest complete submission that can pass every required check. |
